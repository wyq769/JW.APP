## 1. 项目概述

### 1.1 背景

需求方经营/参与的业务属于**塑料机械行业**：为下游工厂制造"片材 / 板材 / 管材 / 薄膜"的**挤出类生产设备（生产线）**。这类设备是"按订单制造"的大型装备，一台线从签合同到出厂通常经历数月，下游客户非常关心"**我的设备现在做到哪一步了**"。

当前该信息大概率靠微信/电话人工同步，存在：信息不及时、口径不一致、反复沟通成本高。本项目目标是建一个网页系统：

- **客户端（对外）**：客户凭设备编号/合同号，自助查询自己设备的生产进度。
- **管理端（对内）**：厂内人员更新各环节状态，客户看到的数据随之变化。

### 1.2 目标（本阶段）

| 阶段 | 目标 | 交付物 |
|---|---|---|
| M0（本次） | 验证信息架构与交互模型，跑通"管理端改状态 → 客户端查状态"闭环 | 技术企划书 + 可运行雏形（纯前端，本机数据） |
| M1 | 接入真实后端与数据库，多端数据一致 | 后端 API + 正式前端 |
| M2+ | 权限、通知、报表 | 见 §12 里程碑 |

### 1.3 范围界定

**本次（M0）做：**
- 双端网页 UI（客户端查询、管理端更新）
- 生产状态的数据模型与状态机（可配置常量，方便后期调整）
- 本机模拟数据（localStorage），零后端、零安装、双击即用
- 预留后端 API 契约设计（后续替换数据层即可）

**本次（M0）不做：**
- 真实登录鉴权（雏形用前端模拟登录）
- 多用户并发/数据同步（localStorage 仅本浏览器有效）
- 短信/微信通知、报表、文件上传
- 移动 App / 小程序

## 2. 术语表

| 术语 | 含义 |
|---|---|
| 设备（Unit）/ 设备订单 | 一台按合同制造的挤出生产线，是状态跟踪的最小主体 |
| 机型（Model） | 设备的产品型号，如"PVC板材挤出生产线" |
| 品类（Category） | 片材 / 板材 / 管材 / 薄膜 四大类，决定编号前缀与机型模板 |
| 阶段（Stage） | 设备订单整体的生产大阶段：原材料进货 → 设备加工 → 试机 → 出厂发货 |
| 子系统（Subsystem） | 一条生产线内部的组成工段：投料、熔融、挤出、冷却、运输、切割、打包 |
| 状态（Status） | 某个阶段/子系统当前所处情形：未开始 / 进行中 / 已完成 / 异常停滞 |

## 4. 需求澄清记录（自问自答）

> 需求方要求：过程中出现的问题通过"自询问"方式解决。以下为本企划的全部关键自问自答，每条包含【问题 → 结论 → 对设计的影响】。

**Q1：这个系统跟踪的"产品"到底是什么？是薄膜/板材本身吗？**
→ 结论：不是。跟踪的对象是**"生产片板管材薄膜的设备"**（即卖出去的生产线），一台设备 = 一个跟踪主体（Unit）。薄膜/板材是客户买设备后自己生产的产物，不在跟踪范围。
→ 影响：数据模型以 `unit（设备订单）` 为核心实体。

**Q2：需求里说的"原材料进货、设备加工、试机"和"投料/熔融/挤出/冷却…"是同一维度的东西吗？**
→ 结论：不是同一维度，是**两个层次**。"原材料进货 → 设备加工 → 试机（→ 出厂发货）"是**订单整体的大阶段**（时间骨干）；"投料、材料熔融、塑性挤出、冷却、运输、切割、打包"是**设备内部的七大子系统**，属于"设备加工"这个大阶段内部的细化进度。
→ 影响：采用"阶段时间线（骨干）+ 子系统进度（加工阶段细化）"双层结构。这是本系统信息架构的核心决策。

**Q3：大阶段止于"试机"吗？**
→ 结论：不止。真实业务中试机合格后还有**出厂发货**，部分厂家还有**客户现场验收/安装调试**。M0 定义 4 个阶段：原材料进货 → 设备加工 → 试机 → 出厂发货；把"客户验收"作为正式版预留阶段（常量中预留枚举位）。
→ 影响：`STAGES` 常量数组，增删阶段只改配置。

**Q4：状态怎么分级？客户看到的是文字还是百分比？**
→ 结论：三级信息——① 订单当前处于哪个大阶段（时间线高亮）；② 每个阶段/子系统的状态（未开始/进行中/已完成/异常停滞）；③ 整体完成度百分比（由规则推算的参考值）。同时保留**变更日志**（时间线式动态），让客户看到"最近发生了什么"。
→ 影响：需要 `computeOverallProgress()` 推算函数 + 日志（logs）子模型。

**Q5：不同品类（片/板/管/膜）的设备，内部子系统构成一样吗？**
→ 结论：不完全一样（例如吹膜机组有模头/风环，管材线有定径套），但抽象层次上都能归纳为"上料→塑化→成型→冷却→输送→切割→卷取/打包"的链路。M0 用统一 7 工段模板；正式版应支持**"机型模板"**：每个机型定义自己的子系统清单，创建订单时按模板实例化。
→ 影响：`subsystems` 作为**数组挂在 unit 实例上**（而非全局枚举硬编码），天然支持每台设备不同的工段构成。

**Q6：数据从哪来？现阶段没有后端怎么办？**
→ 结论：M0 用 **localStorage 模拟数据库**，首次访问注入种子数据；数据层抽象为 `STORE` 接口（list/get/create/update…），将来把实现换成 `fetch(API)` 即可，UI 层零改动。另做 try/catch 降级：localStorage 不可用时退化为内存模式（会话内仍可演示）。
→ 影响：`js/store.js` 单一数据出入口；`js/constants.js` 集中定义一切可调配置。

**Q7：客户怎么查询？会不会泄露其他客户信息？**
→ 结论：M0 用"设备编号 / 合同号 / 机型关键词"模糊搜索（雏形需方便演示）。正式版必须改为**凭据查询**：合同号 + 手机号后四位，或一对一发放"查询码"；客户端字段做白名单过滤（如隐藏成本相关备注）。
→ 影响：M0 客户端全量展示；`sanitizeUnitForClient()` 函数先建好占位（当前原样返回），正式版在此收口。

**Q8：管理端要登录吗？**
→ 结论：要"看起来有"，但 M0 不做真鉴权：前端模拟登录（admin / 123456，sessionStorage 记录），登录卡上明示这是演示账号。正式版走后端 JWT + 角色权限（管理员/计划员/只读观察）。
→ 影响：admin.html 有登录门，逻辑与真实鉴权隔离在 `gate` 函数中便于替换。
→ **【2026-09-19 修订】**M0 引入本地账号表 `operators`（{name, role, pass, createdAt, createdBy}，明文演示存储）：默认王工（主管）/ 李工 / 陈工（操作员）。**有且仅有一个主管**为结构性保证（注册只产操作员、主管不可删、无改角色接口）；主管可注册 / 删除操作员（添加即注册）；动态署名 = 登录账号（废除自由文本操作人）；侧边栏底部显示当前账号。M1 换后端 JWT + 密码散列。

**Q9：状态可以随便改吗？要不要流程校验？**
→ 结论：规则上大阶段应按序推进（不能"未进货就试机"）。M0 做**软校验**：`validateStageTransition()` 返回警告（如"原材料进货尚未完成"），UI 弹提示但允许保存（真实车间存在并行与返工，硬卡死反而不好用）；所有修改强制留痕（自动写日志）。正式版可按厂规切换硬校验。
→ **【2026-09-19 修订】**原材料来自不同进货商，先到料的零件先开工：「原材料进货」与「设备加工」定义为**并行阶段**（`PARALLEL_WITH`），进货未完成时开始/完成加工**不再警告**，进货持续到货、持续输出给加工；试机 / 出厂发货仍按序软校验。
→ 影响：校验是独立纯函数，软/硬模式一个开关。

**Q10：一台设备的状态更新后，另一端怎么看到？**
→ 结论：M0 同浏览器内，管理端写入 localStorage，客户端页面刷新/点击查询即读到最新值（跨标签页可用 `storage` 事件同步，雏形提供"刷新"按钮即可）。正式版由后端保证，可加 WebSocket 推送。
→ 影响：客户端详情页放"刷新"按钮；M1 可无感升级。

**Q11：前端技术栈选什么？**
→ 结论：见 §8 技术选型对比。M0 选**零依赖纯静态（HTML + CSS + 原生 JS）**：双击 index.html 即可运行、无安装步骤、不依赖网络（CDN 在国内不稳定）；代码按"组件化思维"组织（每个渲染函数 = 一个组件），为迁移 Vue/React 留好接缝。
→ 影响：目录结构与代码组织见 §9、附录 A。

**Q12：双端是一个应用还是两个应用？**
→ 结论：**一个项目、三个页面（MPA）**：`index.html`（门户/说明）→ `client.html`（客户端）与 `admin.html`（管理端）。共享 `constants.js / store.js / ui.js / common.css`。MPA 对雏形来说职责最清晰、代码最简单，也最贴近"对外查询页"的真实部署形态（客户端将来可独立部署到公网域名）。
→ 影响：三页结构 + 共享资产。

**Q13：整体进度百分比怎么算才不失真？**
→ 结论：分段权重——4 个大阶段等权 25%；其中"设备加工"阶段按 7 个子系统完成度的平均值折算（避免"加工阶段 50% 完成"被记成 0 或 100 的失真）；异常停滞阶段按 50% 计。
→ 影响：`computeOverallProgress()` 纯函数，进冒烟测试。

**Q14：设备编号怎么编？**
→ 结论：`SX-<品类码>-<年份>-<流水号>`。SX=设备(生产线)，品类码：PC 片材 / BC 板材 / GC 管材 / BM 薄膜。如 `SX-BC-2026-012`。编号唯一，是对外查询主键之一。
→ 影响：`createUnit()` 校验编号唯一 + 格式提示。
→ **【2026-09-19 修订 FR-A12】**订单信息升级：**合同号 + 客户名称置顶**，其后为**设备数量**与**设备编号（可多个）**。
→ **【2026-09-20 修订 FR-A12 v2：订单-设备两级模型】**同单多台**每台独立推进**：`orders[]`（合同号/客户/机型/品类/数量/计划交付）+ `units[]`（每台独立 stages/subsystems/logs，`orderId` 反查订单）；数量 = 编号个数（每台都必须有独立编号与建档）；管理端三级导航（订单列表 → 订单详情每台一卡 → 设备管理页），客户端查任一编号直达该台并可点"同单设备"芯片切换；v1 旧数据自动迁移（旧记录 = 订单，unitIds 拆台深拷贝）。种子重生成：5 张订单 / 8 台设备。
→ **【2026-09-20 增补 FR-A14 / FR-A15】**FR-A14：订单详情页新增"订单动态"——`orderLogs(orderId)` 合并成员设备日志按时间倒序（依赖 FR-A13 的编号前缀，混排自明）；FR-A15：设备管理页重渲染前暂存未保存的滑杆/备注/阶段草稿并回填，修复"保存 A 卡丢 B 卡草稿"。

## 5. 领域模型

### 5.1 实体关系

```
机型模板(正式版) 1 ──── n 设备订单 Unit
Unit 1 ──── n 阶段状态 StageStatus（固定 4~5 个阶段）
Unit 1 ──── n 子系统进度 Subsystem（按机型模板实例化，M0 固定 7 个）
Unit 1 ──── n 日志 LogEntry（所有变更留痕）
```

### 5.2 大阶段状态机（订单骨干）

```
                     ┌────────────┐
                     │  原材料进货  │ procurement
                     └─────┬──────┘
                 done ↓
                     ┌────────────┐
                     │  设备加工   │ processing   ← 内含 7 子系统并行推进
                     └─────┬──────┘
                 done ↓
                     ┌────────────┐
                     │   试机     │ testing ──(blocked: 返修后重试)──┐
                     └─────┬──────┘                                   │
                 done ↓                                               ↑(回到 in_progress)
                     ┌────────────┐
                     │  出厂发货   │ shipping
                     └────────────┘
（预留：acceptance 客户验收，正式版按需启用）

每阶段/子系统状态取值：pending 未开始 → in_progress 进行中 → done 已完成
                                    ↘ blocked 异常停滞（可退回 in_progress）
```

规则（R 编号供测试引用）：
- **R1** 阶段默认按序推进；跳序保存触发软警告（Q9）。**【2026-09-19 修订】**例外：`PARALLEL_WITH` 声明「设备加工」可与「原材料进货」并行——加工开工 / 完工不因进货未完成而警告；试机、发货的顺序校验保留。
- **R2** "设备加工"标记 done 前提：全部子系统为 done（未满足给警告）。
- **R3** 任何变更自动追加日志：`{time, actor, kind, text}`，日志只增不改不删。**【2026-09-20 修订 FR-A13】**`text` 自包含设备编号（`pushLog` 统一前缀：阶段/工段类紧贴编号如 `SX-PC-2026-004「塑性挤出设备」进行中，完成度 25%`；自由动态/订单创建为 `编号 + 空格`），种子动态同规则归一——任何一条动态复制出去都能说明"哪台设备发生了什么"。
- **R4** blocked ↔ in_progress 可互转（返修场景）。**【2026-09-19 修订 FR-A11】**仅大阶段保留四态；**工段改为三态**（等待材料 / 进行中 / 生产完成），且状态为完成度的**派生值**（0% → 等待材料，有进度 → 进行中，100% → 生产完成），不可手工指定——取消工段的"未开始 / 异常停滞"（等待材料统一覆盖，料到即开工）；旧数据按完成度自动归一。
- **R5** `currentStage` 为**派生值**：第一个非 done 的阶段（全 done 则为 shipping），不落库，避免双写不一致。**【2026-09-19 修订】**并行模型下改为：**最深的 in_progress / blocked 阶段**（无活跃阶段则第一个非 done；全 done 停最后）——进货与加工同时进行时如实显示"设备加工"，步骤条对所有进行中阶段高亮。

## 7. 页面信息架构与线框

### 7.1 客户端查询页

```
┌───────────────────────────────────────────────┐
│  ◈ 设备生产进度查询            [管理端入口]      │
```

## 8. 技术选型

| 维度 | 方案 A：零依赖纯静态（推荐） | 方案 B：Vite + Vue3 | 方案 C：CDN 引 Vue3 单文件 |
|---|---|---|---|
| 运行门槛 | 双击 index.html 即用 | 需 npm install + dev server | 需联网（CDN 国内不稳） |
| 安装依赖 | 0 | ~200MB node_modules | 0 |
| 组件化/可维护 | 函数级组织，够用 | 最佳 | 良好 |
| 与 M1 后端衔接 | 数据层单点替换即可 | 直接接 | 直接接 |
| 雏形交付速度 | 最快 | 中 | 中 |
| 风险 | 手写渲染稍繁琐 | 环境/网络门槛 | 离线不可用 |

**结论：M0 采用方案 A**。理由：雏形的第一使命是"最快验证信息架构与状态模型是否正确"，运行门槛必须为零（可直接发给需求方双击查看）；状态机/数据层集中在 `constants.js + store.js`，M1 换后端时这部分是唯一需要动的。代码仍按组件化思维组织，迁移 Vue 时渲染函数可 1:1 改写为组件。

（本机已确认 node v24.18.0 可用，仅用于开发期语法检查与逻辑冒烟测试，不进入运行时依赖。）

## 9. 系统架构

### 9.1 M0 雏形架构（本次）

```
┌─ index.html（门户）────────────┐
│  ┌─ client.html（只读端）──┐   │   js/constants.js  阶段/状态/工段/品类 常量 + 校验/推算纯函数
│  │ client.js               │   │   js/store.js      数据层：localStorage(降级内存) + 种子数据 + 增改查 + 日志
│  └──────────▲──────────────┘   │   js/ui.js         公共渲染组件（徽章/时间线/进度条/吐司）+ 转义防注入
│             │ 读                │   css/common.css   设计令牌 + 双端共用样式
│  ┌─ admin.html（读写端）───┐   │
│  │ admin.js ───────────────┼───┼──▶ localStorage["mcps_units_v1"]（本机模拟库）
│  └─────────────────────────┘   │
└────────────────────────────────┘
```

要点：
- **单一数据出入口**：所有读写走 `APP.STORE`，UI 不直接碰 localStorage。
- **派生状态不落库**：currentStage、整体进度均由读时推算（R5）。
- **XSS 防护**：所有动态文本经 `ui.esc()` 转义后再拼 HTML。

状态枚举：`pending | in_progress | done | blocked`；日志 `kind: stage | subsystem | note | system`。

补充（v0.2）：
- `subsystems[].images[]` 为现场图片记录，`images[].progress` = **上传那一刻的工段完成度**（客户端角标数据源）；
- 工段支持增删改与排序：模板工段用固定 code，新增工段自动编 `custom-N`；重名校验、每设备工段 ≤12 个、每工段图片 ≤12 张；
- 旧数据由 `ensure()` 自动迁移（补 images 字段），无需手动清理。

## 11. 后端 API 契约（M1 预留设计）

数据层按此契约设计，M0 的 `STORE` 方法与之一一对应，届时仅替换实现：

```
POST   /api/auth/login                    → { token, role }
GET    /api/units?q=&stage=&page=&size=   → 分页列表（管理端）
GET    /api/units/:id                     → 详情（客户端按查询码鉴权，字段白名单）
POST   /api/units                         → 新建订单（管理端）
PATCH  /api/units/:id/stages/:stageKey    → 更新阶段 { status, note }
PATCH  /api/units/:id/subsystems/:code    → 更新工段 { status, progress, note }
POST   /api/units/:id/logs                → 追加动态 { text }
```

约定：所有变更类接口服务端**自动写日志**（与 R3 一致）；阶段跳序返回 `422` 附警告信息（对应软校验，由前端决定拦截或放行）。

## 14. 风险与待定（需真实业务校准）

| # | 风险/待定项 | 现行处理 | 校准时机 |
|---|---|---|---|
| 1 | 阶段/工段名称与厂内真实叫法有出入 | 常量集中定义，10 分钟可改 | M0 评审时拿真实工艺单核对 |
| 2 | "试机"内部其实还有子环节（空载/负载/连续运行） | M0 记在备注与日志里 | M2 决定是否升级为二级阶段 |
| 3 | 客户端开放搜索有信息泄露风险 | `sanitizeUnitForClient()` 占位，正式版收口为查询码 | M1 必做 |
| 4 | 软校验可能放出不合规状态 | 全部变更强制留痕可追溯 | 按厂规切换硬校验 |
| 5 | localStorage 上限/清理导致演示数据丢失 | 一键重置种子数据 | M1 上真实数据库 |
| 6 | 同浏览器多标签页不同步 | storage 事件/手动刷新 | M1 由后端保证 |
| 7 | localStorage 约 5MB 配额限制图片存储量 | 上传前 Canvas 压缩（长边 1000px / JPEG 68%）+ 每工段 ≤12 张 + 超限/超配额明确报错 | M1 图片迁移对象存储 |

## 15. M0 实施任务分解（本次雏形的执行清单）
